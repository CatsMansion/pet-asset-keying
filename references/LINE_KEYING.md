# 顺着勾线切 · Key by the Line Art

> 这一招不是我想出来的，是被一句外行话点醒的。
> 那天我调阈值调了一整天，对方看了一眼原图说：**「人物本身是有勾线的，顺着勾线切割其实会很干净的。」**

---

## 问题不在阈值，在"边界"根本不在那儿

先说我之前的思路有多理所当然：量背景色，算每个像素到背景的颜色距离，大于阈值的算角色。纯色底嘛，这有什么难的。

难的地方在于**边界那圈像素长什么样**。

动漫素材的边缘不是一刀切开的，是抗锯齿渲染出来的。从"完全是背景"到"完全是角色"之间，横着大概一到两个像素的过渡带，里面的颜色是 `α·角色 + (1−α)·背景` 的混合。我的阈值就落在那条带子里。

落在带子里意味着什么？意味着**我在一个没有正确答案的地方找正确答案**：

- 阈值紧一点 → 边界切在靠外，那圈混了背景色的像素算角色 → 留下一圈暗边
- 阈值松一点 → 边界切在靠内 → 开始吃角色，细结构先死

这就是那圈"暗边"的来源。它不是参数没调好，是**阈值法的边界位置天生就是模糊的**。

而勾线不一样。勾线是一条深色的、高对比的、有明确内外之分的线。它本来就被画在那儿。**那是一道现成的切割线。**

---

## 怎么把"顺着勾线"变成代码

工具有了：泛洪。

勾线是深色的，距背景远，泛洪过不去。所以从画面四边往里灌，灌不到的地方就是角色。

```python
passable = (距背景 < TOL_OUT)        # 可通行 = 颜色接近背景
从画面四边取连通域 → outside
角色 = ~outside                       # 勾线天然阻断了泛洪
```

这段话最大的好处是**参数不敏感**。实测同一段素材（768×1152，107 帧，背景 `(96,96,96)`），把 `TOL_OUT` 从 20 一路加到 65：

| TOL_OUT | 切出的角色像素 |
|---|---|
| 20 | 148825 |
| 65 | 143556 |

差 3.5%。因为泛洪的边界是**勾线**，不是阈值——阈值只负责"判断哪些像素能走"，而真正拦住它的是那条线。**参数只要落在"背景和勾线之间"这一大片区间里，结果都一样。**

这一点很舒服。它意味着这套东西换素材、换角色、换背景亮度，都不用重新标定。

---

## 第二个问题：角色**内部**也有背景

第一版我只做了上面那一步。交出去之后被打回来了，指着膝弯和辫子旁边：**这几块灰的是什么。**

是背景。角色手叉腰、辫子垂在肩上、腿弯起来的时候，会围出一些**封闭的空腔**，里面的背景色跟外面不连通，泛洪到不了，于是被整个当成角色留下了。

解法是再来一次泛洪，从空腔里面往外灌。但这一次有两个坑，都踩过。

**坑一：种子不能用几何质心。**

我第一版就是取每块候选的质心当种子。直到被指出：

> ⭐ **「封闭空间如果是月牙型/异形，不能放中间，泛洪一定要放在对应的背景颜色上。」**

月牙形的质心根本不在月牙里面，在它对面的角色肉上。从那儿泛洪，就把角色啃掉一块。

正确的做法是取**块内距背景最近的那个像素**当种子：

```python
dm = np.where(block, dist_bg, INF)
seed = argmin(dm)          # ⭐ 一定是"最像背景"的那个像素
```

种子距离实测在 0 到 4 之间（L1），也就是说它确实落在背景色上而不是过渡色上。这一步还有个副作用是自带守门：如果一块候选里最像背景的像素都不够像背景（距离大于 `SEED_MAX`），那这块根本不是空腔，整块不动。

**坑二：泛洪必须锁在角色内部那个掩膜里。**

不锁的话它会顺着自己刚切出来的抗锯齿带往外漏，一路漏到画面外。实测漏过一次 **73 万像素**，整张图几乎被清空。

## 软边怎么来的

二值掩膜边是硬的，直接出图会有锯齿。但软边不能随便做。

先说一个反直觉的：**不能直接用距离变换。**

我一开始写的是 `alpha = clip(dist/band + 0.5)`，看着很合理——离边界越远越不透明。跑出来量了一下，半透明像素占比 **0%**。原因很好懂：距离变换给的是整数距离，`1/2+0.5=1`、`0/2+0.5=0.5`，再往下就没有档了，二值化了。

现在用的是**先内缩 1 像素，再高斯模糊**。

为什么要内缩：泛洪停下来的位置是"第一个距背景 ≥ TOL_OUT 的像素"，那是抗锯齿带上背景混色还占九成的位置。**比理想的 50% 覆盖线还往外多留了大约一个像素的背景混色。** 内缩 1 像素正好把它压回去。

```python
m = binary_erosion(char, iterations=1)
alpha = gaussian_filter(m.astype(float), 0.8)
```

另外还有个 `defringe`：半透明带里的颜色不取原像素，取**最近实心像素的颜色**。只改颜色不改 α，所以不会削角色，效果是那圈灰读起来像阴影而不是脏边。

## 把勾线本身保护起来（第二轮）

上面那套做完，交出去之后又被打回来了。这次指的不是空腔，是**线条**：

> ⭐ **「原图里我看到的勾线，在这一版里已经被啃掉一些了。」**

我一开始没懂——泛洪不是被勾线挡住的吗，怎么还会啃到勾线？

挡住泛洪的是**够粗的**勾线。但 pass2 的 `allow` 区是"距背景 < TOL_HOLE 的像素"，**线条本身如果不够深、或者处在过渡带上，它就在 `allow` 里**。泛洪从空腔出发，遇到这种细线就顺着啃过去——线条连着旁边的脏块一起没了。

所以要把线条**从 `allow` 里整个剔除**，变成泛洪不许穿过的墙：

```python
LINE = inside & (亮度 < LINE_LUM) & (开运算 LINE_R 后"被吃掉"的像素)
allow = allow & (~LINE)          # ⭐ 硬墙
```

关键在那个"被吃掉"。开运算（先腐蚀后膨胀）会把**比结构元窄**的东西抹掉。所以：

```
m      = 暗色像素
opened = 对 m 做开运算
LINE   = m & (~opened)        # ⭐ 开运算吃掉的 = 局部宽度不足的 = 线条
```

这条判据踩过一个坑：**两个条件缺一不可。**

| 用的判据 | 抓出多少 | 问题 |
|---|---|---|
| 只用几何（开运算） | 604 px | ⛔ 太少，漏一大堆 |
| 只用暗色（不看粗细） | 66362 px | ⛔ 把深色外套的暗部全算进去了 |
| **两个同时** | **9156 px** | ✅ 刚好 |

效果：

| 帧 | 挖掉的线条（无保护 → 有保护） | 降幅 |
|---|---|---|
| pat#60 | 475 → **27** | −94% |
| walk#36 | 75 → 23 | −69% |
| sleep#12 | 25 → 10 | −60% |

⭐ 而**总挖量几乎不变**（pat 那帧是 2296→1773，降的正好是那 475px 线条本身）。
**说明保护线条没有妨碍挖背景。**

还有一个如实记录：**残差收不干净。** 线条交汇处、端点处局部会变宽，宽度超过 `2×LINE_R` 就不算"细"了，几何上抓不到。我把 `LINE_R` 从 1 试到 3，**残差纹丝不动（49/41px）**——

> ⭐ **说明这不是"参数没调够"，是检测方式的极限。**
> 换个说法：残差只有约 0.03% 的角色面积，已经可以接受了。

## 发丝外围那圈灰边（第三轮）

再交出去，又被指了位置：

> ⭐ **「马尾和肩膀之间，刘海和脸颊之间」**——「发丝外围灰边没清」。

这次是**抗锯齿留下的连续过渡带**。它的位置很尴尬，夹在两个阈值中间：

- 距背景太远，够不到 pass1 的 `TOL_OUT` → 泛洪过不去 → 被判成"角色内部"，留下
- 距背景又不够近，够不到 pass2 的 `SEED_MAX` → 不构成候选 → **永远轮不到它被挖**

第一反应当然是放宽 pass2。**试了，不行。**

| SEED_MAX / TOL_HOLE | 洞数 | 挖掉 |
|---|---|---|
| 12 / 40（现行）| 8 | 3195 px |
| 40 / 60 | 15 | 4895 px |
| 60 / 80 | 16 | 9062 px |
| ⛔ 80 / 100 | **88** | 32646 px |

破口在 60→80：**洞数从 16 暴涨到 88**，泛洪咬进发丝内部了。**灰边和发丝内部的色差太小，一提阈值就一起咬。**

所以换成另一条路：**不动几何，只降 alpha。**

```python
t = clip((d - D0) / (D1 - D0), 0, 1)     # d 小 → t 小；d 大 → t 大
alpha = min(alpha, t)                     # ⭐ 只降不升
```

d 小（更像背景）→ alpha 压向 0；d 大（角色实色）→ alpha 保持 1。因为**不挖洞、不腐蚀**，所以不会像放宽 pass2 那样咬穿发丝。

⛔ **但第一版把眼睛和衣服挖空了。**

根因是：**`d`（距背景色的距离）分不开「灰边」和「深色角色色」。**
银白发丝旁边的灰边 d 在 40~110；可她的眼睛是深灰绿、外套是深藏青，**离背景灰本来就近**（d 60~90）——被一起削成了半透明。

✅ 加两道硬约束：

| 约束 | 怎么判 | 为什么 |
|---|---|---|
| **亮度闸** | 亮度 < 118 → 豁免 | 灰边亮度约 100~160，眼睛约 60~110，外套约 40~80 |
| **勾线豁免** | LINE 掩码内 → 不动 | 勾线是角色，且必须实心 |

效果（正反两面都有）：

| | 去灰前 | 去灰后 |
|---|---|---|
| 半透明占比 | 5.2% | **12.1%** |
| 角色内 alpha≥250 | 94.6% | 88.3% |

⭐ **半透明占比上升是预期的、正确的** —— 那正是把"实心的脏灰边"换成了"干净的半透明过渡"。
目检（青底放大）：马尾外缘、发梢末端的深灰脏边消失，**发丝本体零损失**。

## 补最后那点漏网的小灰缝（pass3）

再往后，反馈变成：

> ⭐ **「扣完之后还有几个小像素点没扣掉。」**

我前两轮一直在调**颜色阈值**（`SEED_MAX` 12→16→20→32）。**只救回来 400px，而且开始咬角色色**——因为这些残留块的 `d` 落在 12~30 的过渡带，放宽阈值就会把"发丝阴影"一起放进来。

✅ 真正管用的是**三项判据同时满足**：

```python
① 包住率 ≥ 90%     # 块外一圈基本是角色（不是贴外轮廓、也不是大开口）
② 像背景           # d < TOPO_D_MAX 且 RGB 三通道极差 ≤ TOPO_SAT
③ 面积 ≥ TOPO_MIN
```

⭐ **第 ② 条里的"中性灰"是关键一票否决。**
纯灰背景的 RGB 三通道极差 ≈ 0；而角色的阴影带绿调或暖调。
**光靠 `d` 分不开这两者，靠"中性"能干净分开** —— 实测把 5 个阴影块全挡住了。

实测：全 8 个动作共 **71 块 / 5355 px**（平均 36px/帧），**反向 = 0**（严格只多挖该挖的，绝不新挖）。
⭐ `反向 = 0` 是这类"补漏"改动**最关键的验收项** —— 它证明没引入新的误伤。

## 跟原来的 matting 路线是什么关系

不是替代，是分工。

| | 顺着勾线切 | 传统 matting（pymatting ∩ isnet-anime）|
|---|---|---|
| 靠什么找边界 | **勾线**（结构）| 颜色阈值 + 语义分割 |
| 硬边（人物、道具、描边插画）| ⭐ 干净，且参数不敏感 | 边界落在模糊带里 → 留暗边 |
| 发丝级细结构 | ⚠️ 细到没有勾线的地方就无从下手 | ⭐ 这才是它的主场 |
| 速度 | 0.2s/帧（768×1152，纯 CPU）| 秒级 |
| 需要模型 | 不需要 | 需要（isnet-anime 168MB）|

**素材上有勾线就用勾线切，没有勾线的细结构交回 matting。** 这两个的短板不重叠，所以也可以串起来用。

## 它现在做不到什么

**勾线断口会漏。**

泛洪唯一的失败模式就是"线断了"。如果某个角度的勾线没画连（或者被高光、被背景色接近的填色打断），泛洪会从断口钻进去，在角色身上留下一块灰。

我实测遇到过一次，在某个动作的腿和鞋那一带。现在的做法是先对可通行区做闭运算把断口补上，但它不是万能的——**断口宽了补不上，补狠了又会把细结构连成一片。**

**所以这套东西现在的状态是：方向确定是对的，边界情况还在收。**

还有一件事得说明白：它不需要模型，也不需要 GPU，但**它假设你的素材有勾线**。没有描边的写实素材、渐变背景、多个主体，别用这个。

## 两个"静默不挖"的 bug（值得单独讲）

这两个 bug 的症状和上面所有问题的症状**长得一模一样：漏抠。**
但它们和阈值一点关系都没有，根因都在**内部记账**。我绕了好几轮才找到，所以写下来。

### bug 一：种子落在被剔除的掩码上

我给线条做了硬墙之后，`allow` 里剔掉了线条掩码。**但挑种子的代码没检查这件事。**

于是有时候种子正好落在被剔掉的那个像素上——`allow[种子] == 0`。

然后是关键：

```python
cv2.floodFill(tmp, mk, (sx, sy), 2, 0, 0, flags=...)
```

> ⛔⛔ **`cv2.floodFill` 不检查起点的值。**
> 起点已经是 0 时，它会把**整片 0 连通区**当成填充区。

实测淹掉 **954,580 px**（≈ 整张图的 960,000）。然后被 `MAX_HOLE`（单块上限）拦下 → **整块被 skip**。

⭐ **后果不是"多挖"，是"该挖的静默不挖"。**
规模：**19/38 个候选块中招，整整一半。**

✅ 修法：挑完种子后**断言它落在 allow 上**；不在就在「块内 ∩ allow」里重挑 `d` 最小的那个：

```python
if allow[sy, sx] == 0:
    cand_ok = blk & (allow > 0)
    if not cand_ok.any():
        continue                     # 整块被线条覆盖，放弃
    dm2 = np.where(cand_ok, d, INF)
    sy, sx = np.unravel_index(int(np.argmin(dm2)), d.shape)
```

### bug 二：泛洪掩码那段代码被整段复制了两遍

`newly` / `fa` / 超上限判断 / `char[newly] = False` —— 连着贴了两次（第二遍还漏了个字段）。

后果也**不是多挖**：

1. `removed` 被**重复累加** → 触发了 `MAX_REMOVE_FRAC` 单帧总闸
   → 整帧 `char = inside.copy()` **回滚到 pass1 状态** → **该挖的全没挖**
2. `holes.append` 重复 → 日志里的块数虚高

### 这两个 bug 的共同教训

> ⭐══ **「上限类」逻辑会掩盖 bug。** ══⭐
>
> `MAX_HOLE` 把 954,580 拦下来了，程序没崩、没报错、日志只有一句"skip: 泛洪超上限"。
> **看起来像"正常的保守跳过"，实际是 bug 在隐身。**
>
> ✅ 所以：**任何"超上限就跳过"的分支，都必须带计数器或告警。**
> 否则你会以为它在保护你，其实它在替你藏问题。

> ⭐══ **上游掩码吃掉下游的种子，是串联模块的通用坑。** ══⭐
>
> 线条掩码本身是对的，种子挑选本身也是对的。
> **两个各自正确的模块串起来，交集处没人验证。**
>
> ✅ 教训：**串接两个模块时，必须显式校验"上游的输出满足下游的输入假设"。**

> ⭐══ **验收要看「反向 = 0」，不是「多挖了多少」。** ══⭐
>
> 修一个"漏扣"类 bug，最关键的验收**不是补回来多少**，
> 而是**有没有新挖不该挖的**。后者才是没引入新伤害的证据。

## 用法

```bash
# 单图
python line_keying.py 输入.png 输出.png

# 帧序列（自动共用同一个背景色）
python line_keying.py ./frames/ ./keyed/

# 关掉内部空腔处理，只看外部（调参时很有用）
python line_keying.py in.png out.png --no-hole-fill

# 逐项关掉看效果（对照用）
python line_keying.py in.png out.png --no-line-protect
python line_keying.py in.png out.png --no-dew
python line_keying.py in.png out.png --no-small-fill
```

参数只有三个值得动的，而且都很好判断：

| 参数 | 默认 | 什么时候动 |
|---|---|---|
| `--tol-out` | 30 | 背景和勾线对比不够强时放大 |
| `--seed-max` | 12 | 背景是渐变、估计不准时放大 |
| `--erode` | 1 | 边缘还留着一圈灰就加到 2 |

它跟 `pure_bg_keying.py` 一样会自己报数：背景色、切出多少像素、内部空腔切掉几块、**误挖的洞有几个**。

最后那个数字要单独说一句：它会把空腔处理**故意**切掉的区域先补回去再数洞，所以它只反映"误挖的洞"。⛔ 而且它不能单独用来判断好坏——**一个被切掉半个头的角色，也不会有洞。** 必须同时看实心面积。

## 结论（就一句）

**做图之前先问一句：这张图里有没有现成的边界可以直接用。**

我调了一整天的颜色阈值、模型交集、时域平滑，全都是在**我假设的边界**上做文章。而边界本来就在那儿，是画上去的。
