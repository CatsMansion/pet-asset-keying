## ① ⛔ "颜色清理"（距背景 < N 的像素直接扣掉）

**看起来最合理，实际最坑。**

```python
# ⛔ 别这么干
hit = (alpha > 0) & (np.abs(rgb - BG).sum(axis=2) < 30)
alpha[hit] = 0
```

**为什么错**：你会以为"角色色板离背景很远，所以 N=30 一定安全"。

**实测反例**：某角色**主色板**离背景最近 59 → 于是设 N=30 → **结果在角色内部挖出了洞** ⛔

**原因**：**色板距离只是"颜色代表值"的距离，不是"每个像素"的距离。**
角色**内部颜色交界处的抗锯齿像素、以及阴影**，都可能把实际像素拉到背景附近。

> ⭐ **教训：「色板距离」不能用来担保「像素级安全」。**

**✅ 正确做法**：不做这类清理。
要判断"有没有挖坏"，**用程序内置的洞数自检**：

```python
from scipy import ndimage
filled = ndimage.binary_fill_holes(mask)
holes = filled & (~mask)           # 内部洞
# ⭐ 洞数 / ≥8px 洞数 / 洞总面积 —— 加任何后处理前后对比，变多就是挖坏了
```

**这个检验只要一秒。加后处理之前先跑它。**

## ② ⛔ 精确去污染 `F = (C − (1−α)·BG) / α`

**理论上很漂亮**（已知均匀背景，可以直接解出去混合后的前景色）。

**实测**：污染像素 **443 → 5305**，**反而更糟** ⛔

**原因**：这个公式对 α 的精度极其敏感。
- α 偏大 → 前景色被拉暗
- α 偏小 → **除以小数字 → 颜色被过度放大** → 反而更饱和

而我们的 α 来自 matting 估计，**在发丝这种细结构上误差本来就大**。

---

## ③ ⛔ 混合方程反解 `α = |C − BG| / |F − BG|`

思路：既然 `C = α·F + (1−α)·BG`，而 BG 已知、F 已由 matting 估出，那 α 就能精确算出来。

**实测**：**边缘出现满圈麻点噪点** ⛔

**原因**：
- `|F − BG|` 在细结构上可能很小 → α 被放大到 1
- F 本身的估计误差被直接搬进 α
- 结果是 α 空间上**不连续** → 观感是"噪点"

---

## ④ ⛔ 分块放大建模（把头部裁出来放大 2x 单独跑模型）

思路：模型输入分辨率有限，把重要的头部放大后单独跑，让它"看到更细的发丝"。

**实测**：污染像素 **443 → 19454**，**显著变差** ⛔

**原因**：**分块打断了 α 的空间连续性。**
- 分块边界处不连续
- 放大后的 α 缩回原尺寸时插值引入误差
- 分块区域与其他区域的统计算法不一致

> ⭐ **要提升分辨率，应该整体处理，而不是分块。**

## ⑤ ⛔ 只用语义模型、不开 `alpha_matting`

```python
# ⛔ 这样的 alpha 几乎只有 0 和 255
remove(img, session=new_session("isnet-anime"))
```

**实测**：污染像素 **7724**（与"完全不做"一样）⛔

**原因**：不开 alpha matting 时，模型输出的是**硬掩膜** ——
**只能表达"是/不是"**，无法表达"这里是 30% 背景"。而**发丝边缘恰恰全是这种半背景像素**。

**✅ 必须开**：

```python
remove(img, session=new_session("isnet-anime"),
       alpha_matting=True,
       alpha_matting_foreground_threshold=240,
       alpha_matting_background_threshold=10,
       alpha_matting_erode_size=8)
```

## ⑥ ⛔ "两版颜色"方案（α 取 A 版、RGB 取 B 版）

思路：如果不同背景色各出一版素材，就能"几何取分割干净的那版，颜色取污染不可见的那版"。

**为什么不行**：⛔ **视频里两版姿势不同 → 对不齐。**

- 静帧（一张图）勉强可以：靠角色 bbox 对齐 + 缩放
- **视频 / 序列帧完全不可行**：每一帧的姿态都不同，两版之间没有稳定对应关系

> ⭐ **所以抠图必须在"单一版本"上解决。**
> 这也正是本工具选择"两种方法在同一张图上取交集"的原因 —— **单版本，无对齐问题。**

## ⑦ ⛔ 用「指标变好」来决定取舍

这一条不是某个后处理，是一种**做决定的方式**。同一天我在自己的链路上加了两步后处理，每一步的硬指标都变好：

| 我加的步骤 | 指标表现 | 观感结果 |
|---|---|---|
| 去投影（去掉源视频自带的那圈中性暗灰） | 边缘中性暗灰像素 **−9.6%** | ⛔ 更差 |
| 时域平滑（对 α 逐像素时域中值） | 帧间抖动 **−15~46%** | ⛔ 更差（还把边上糊了）|

两次都是"指标明确变好 → 装机 → 被一眼看出变差 → 回退"。**因为这两个改善都是拿观感换来的**：平滑换掉的是边的锐度，去投影换掉的是画面的立体感。

> ⭐ **指标只能用来【发现问题】，不能用来【评判好坏】。**

还有一个更隐蔽的版本：**单一指标会被另一种缺陷骗过去。**

- **「洞数」→ 被「截断」骗过。** 角色被切掉半个头，那块当然不会有洞，洞数于是变得很漂亮 ⛔
- **「边缘暗灰」→ 被「深色衣服」骗过。** 角色本身是深色的，暗环指标就失去意义
- **「二值抖动」→ 被「软边」骗过。** 软边的二值化边界当然抖，但那不是缺陷

✅ 所以定下三条：

1. **洞数必须和「实心面积」一起看**：面积明显偏小 + 洞少 = 截断，不是干净
2. 任何数值排序之后，**对前 1~2 名做目检**再下结论
3. 效果类改动 **先出对比图给人看，再装机** —— 中间产物都在手里，出对比几乎零成本

## ⑧ ⛔ 用「归一化比值」当判据（分母被扫描变量决定）

**这个坑很隐蔽：指标完全正确，但它是循环的。**

我扫 `MIN_HOLE`（封闭块面积下限），用了 `ratio = 泛洪面积 / 块面积` 当判据。
跑出来漂亮极了：真洞 ratio 1.1~1.5，跑飞 14~52 —— 分界线清清楚楚。

**然后发现它是自相矛盾的。** 铁证是同一帧上的同一笔泛洪：

```
MIN_HOLE=40:  blk=389  flood=650   → ratio 1.7×   判「真洞」✅
MIN_HOLE=10:  blk= 20  flood=650   → ratio 32.5×  判「跑飞」⛔
```

**同一笔泛洪、像素级完全相同**，只是被不同大小的块"认领"，判据就翻了个面。

**机理**：块划分本身**不依赖 `MIN_HOLE`**（骨架算法决定的），
但泛洪是**按块面积升序**跑的：
- `MIN_HOLE=40` → 门槛 56px → 小块被跳过，**389px 的块先跑**
- `MIN_HOLE=10` → 门槛 14px → **20px 的小块抢先跑**，挖掉同样那 650px

> ⭐ **`ratio` 的分母（块面积）是被扫描变量人为筛选过的，不是自然量。**

✅ 正确做法：
- 换成**不依赖扫描变量的绝对量**（这里是"最终实心面积"）
- 或者**从物理意义出发找判据**（这里是"泛洪像素距角色原始外轮廓的深度"）

**判据成立的那个（泛洪深度）确实分得开：**

| 泛洪 | 深度中位 | 真面目 |
|---|---|---|
| 117 px | **7.0 px** | ✅ 细缝（该挖）|
| 650 px | **36.4 px** | ⛔ 吃进实心区 |
| 127 px | 6.1 px | ✅ 细缝 |
| 828 px | 59.1 px | ⛔ 深吃 |

> ⭐ **分界线干净：深度中位 <8px = 细缝；>30px = 吃进实心区。**

## ⑨ ⛔ `cv2.floodFill` 从一个"值为 0"的像素起跑

**这是我这套工具里最阴的一个 bug** —— 症状表现为"漏抠"，看起来像阈值问题，其实是 API 行为。

```python
allow = ((d < TOL_HOLE) & inside)
allow = allow & ~LINE_MASK              # 剔除线条（硬墙）
...
cv2.floodFill(tmp, mk, (sx, sy), 2, 0, 0, flags=8 | FLOODFILL_MASK_ONLY | ...)
```

**如果种子 `(sx, sy)` 正好落在被剔除的那个像素上**（`allow[种子] == 0`）：

> ⛔⛔ **`cv2.floodFill` 不检查起点的值。**
> 起点已经是 0 时，它把**整片 0 连通区**当作填充区。

实测淹掉 **954,580 px**（≈ 整张图的 960,000，也就是"全图减掉 allow 那 5248px"）。
然后被单块上限拦下 → **整块被 skip → 该挖的静默不挖。**

**规模：19/38 个候选块中招，整整一半。**

✅ 修法：挑完种子后**断言它落在掩码上**；不在就在「块内 ∩ 掩码」里重挑：

```python
if allow[sy, sx] == 0:
    cand_ok = blk & (allow > 0)
    if not cand_ok.any():
        continue
    dm2 = np.where(cand_ok, d, INF)
    sy, sx = np.unravel_index(int(np.argmin(dm2)), d.shape)
```

> ⭐ **通用规矩：凡是"先造掩码、再从某像素起泛洪"的写法，都必须显式校验起点在掩码内。**
> 而且这类校验要写成**断言**，不能靠"我挑种子的时候应该不会挑到那儿"。

## ⚠️⑩ 别拿「处理过的输出」当基准

**这个不是某个算法的坑，是验证方法的坑。**

我用了一个已经处理过的版本当"原样基准"来对比新改动。跑了一整轮，结论全是错的——
**因为那个基准本身就已经重度处理过了**（它自己就啃掉了 982~1739 px 的角色/线条）。

> ⭐ **拿坏样本当金标准，比出来的结论全废。**

✅ 正确顺序：**确定一个"最上游、变量最少"的基准**
- 跟"源素材"比，不要跟"上一版产物"比
- 验证某个参数有没有用，要在**同一源帧、同一流程**上只差那一个变量地比
- ⛔ 拿多轮补丁拼出来的产物做 A/B，几何噪声会把真信号淹掉
  （实测：装机几何 = 6 条规则 + 2 个事后补丁，**新版无论怎么拟合都残留 ±1px 亚像素差**，
   在角色边缘一整圈累积 → 差异率 30~48%，把真信号彻底淹没）

**结论错了不可怕，是被自己的图骗了才可怕。**

| 陷阱 | 后果 | ✅ 规避 |
|---|---|---|
| **深灰底看灰色残留** | 残留是 `(98,98,98)`，深灰底 `(72,72,72)`，只差 26 → **完全看不出来** | 用**浅青** `(200,240,245)`，灰点极显眼 |
| **最近邻放大判边缘质量** | 锯齿伪影 → 把**真灰缝**误读成"啃了发丝" | 用 `LANCZOS/AREA` 放大，**且必须同时给 1:1 对照** |
| **填充式标注** | 把"挖了一小块"渲染成"挖了一大片" | 用**细轮廓线**（1px，不填充） |

⭐ 另外：**深色角色做物性目检，单一底色一定不够。** 深底上深色外套糊成一片，白底又丢掉银发边缘。
**要多底组合**：浅青（默认）/ 纯白（看暗部边缘有没有亮边）/ 纯黑（看亮部边缘有没有暗边）/ 棋盘（看 alpha 边缘）。

## ⚠️⑫ 验证"你施加的变换"时，必须留一份【没施加】的对照

**症状**：我做完跨段缩放，写了个验证脚本逐帧量输出帧的外接框尺寸变化，
跑出 **22.51%**（阈值 12%）—— 看着像缩放做坏了。

**⛔ 这个指标是错的。** 那段素材本身带"起身"动作，外接框从 193px 一路变到 489px。
**我把「素材本征动作」和「我施加的缩放」混在同一个数里量了** —— 当然巨大。

**✅ 正确做法：量比值。**

```
r_i = 新尺寸_i / 旧尺寸_i          （旧 = 没施加变换的那一份）
```

素材自身的动作在比值里被约掉，剩下的才是你施加的缩放：

```
r: 1.0966（躺姿） → 1.0000（站姿）
逐帧最大变化 1.268%          ✅ 平滑
```

| | 量什么 | 实测 |
|---|---|---|
| ⛔ 错 | 输出帧尺寸的逐帧**绝对**变化 | **22.51%** → 误判成失败 |
| ✅ 对 | `r = 新/旧` 的逐帧变化 | **1.268%** → 正确 |

⭐ 一般化：**要验证"我施加的变换"，就得有一份"没施加变换"的对照，然后量两者之比。**
只看结果本身的绝对指标，一定会把素材自身的性质算进来。

⚠️ 和 ⑩ 是同一件事的两面：⑩ 说"别拿处理过的输出当基准"，⑫ 说"没有基准时，绝对指标会骗你"。
**两条合起来的结论只有一句：验证必须有对照。**

## ⚠️⑬ 两类【不报错、结果全错】的静默错配

这类最贵 —— 程序不崩、不警告，输出看着挺正常，**但你整批结果都是错的**。
写跨段缩放那版工具时，两类都踩到了。

### ① 涉及取整的系数，小数位给不够

我参数写成 `--seg 0-21:1.0167`（而不是精确的 `488/480 = 1.0166667`）：

```
跟全精度版逐字节比对 → 107 帧里差了 1 帧（3.2 万像素不同，单像素最大差 156）
换成全精度再跑     → 107 / 107 逐字节一致
```

根因不是数值误差，是**取整边界**：缩放尺寸算的是 `int(round(高度 × 系数))`，
系数差 `3e-5`，在某一帧上刚好跨过 `.5` —— 高度差 1px，整幅图跟着位移，
于是"整帧都不同"。

> ⭐ 这种 bug 最恶心的地方：**只影响个别帧、肉眼看不出来，
> 而且一旦拿它当"基准"去验后面的步骤，误差会一直传下去。**
> 涉及取整的系数，一律给全精度。

### ② 帧序列排序别用字典序

我按 `sorted(os.listdir())` 列帧。而装机帧名是**不补零**的
（`sleep_out_0.png` … `sleep_out_29.png`），**字典序会把 `_10` 排到 `_1` 前面** ——
新旧帧**配对全错位**。

```
错位后：r 末 = 1.0858，逐帧最大变化 10.000% @#13   → 看着像"有 10% 跳变"
按数字排序后：1.0000，1.268% @#17                  → 和原始脚本完全对上
```

⛔ 在**缩放**那条路上更危险：排序错了，**系数会被配到错的帧上**，
不报错、不崩、结果看着还挺正常。

> ⭐ 统一走一个"按文件名最后一个数字段排序"的函数，别在哪都写 `sorted()`。

**这两类的共同特征**：错误不在数值里，在**顺序和精度**里。
所以检查它们也得用同一类手段 —— **找一个"应该完全一致"的对照，做逐字节比对**。
（⑫ 说的也是这件事。）

## 附：已知的**物理下限**（不是坑，是边界）

**发梢最末端的一圈「混合像素」无法自动消除。**

那些像素的颜色 = `α·前景 + (1−α)·背景`，**既不是背景也不是前景**。
任何阈值 / 二值方法都只能在两者之间二选一：

| 选择 | 后果 |
|---|---|
| 判成背景 | **发丝被削细**（更难看）|
| 判成前景 | **留一圈淡灰**（可接受）|

> ⭐ **这是物理下限，不是参数没调好。**

**判断"到没到下限"的方法**：

```
换 2–3 种完全不同的思路，都得不到改善 → 到下限了
→ 该转向【源头】或【人工】，而不是继续调参
```

转向哪里：

1. ⭐ **源头**：出图时让发梢**更"硬"**（更高对比、更少柔化）→ 混合像素更少
2. **人工**：用 Procreate / Photoshop 图层蒙版精修**关键帧**，再反推规则批量应用
3. **接受**：在中灰底上肉眼已很难看出 —— 大多数场景够了
